## Two real bugs found and fixed on real hardware (IC-705)

- **CI-V echo-back misread `channel-tools/channel-picker.py` and
  `program_channels.py`.** This IC-705 echoes a CI-V command back over USB
  as its own frame before sending the real reply. Both scripts read only
  up to the first `\xfd`, which was that echo, not the actual reply -
  Channel Picker's "Go to Channel" succeeded or failed essentially at
  random depending on serial timing, and `program_channels.py`'s writer
  (which only rejects an explicit NG) would have silently accepted a
  misread echo as success without ever checking the real result. Fixed
  with a shared `read_civ_reply()` that skips a frame identical to what
  was just sent and returns the next one - correct whether echo back is
  on or off. Verified live: 17/17 memory groups selected and read back
  correctly, repeatably, across fresh open/close cycles, matching the
  app's own exact code path.
- **A second bug found through the first one**: the AmRRON group (16) on
  this IC-705 turned out to be genuinely unprogrammed (its raw memory
  content was a blank placeholder byte, not real data, confirmed by a
  direct CI-V memory-content read) - not a symptom of the echo bug, just
  never written to this particular radio. Programmed via
  `program_channels.py` and spot-checked against the radio's actual
  stored bytes (distinct frequency and name per channel), per this
  project's standing practice of not trusting "0 failed" alone.
- **Fldigi's "Use Hamlib" only gives CAT frequency control, not PTT.**
  A separate checkbox, "PTT via Hamlib command" (`HAMLIBCMDPTT`), was
  off - Fldigi showed itself transmitting (Tune lit, audio generated) but
  the IC-705 never actually keyed, since CAT reads/frequency worked the
  whole time and masked the problem. Fixed in the live config (with
  Fldigi closed first, since it rewrites its settings on exit) and in
  `Start_Fldigi.sh`'s automatic first-run Hamlib setup. Fldigi's own help
  text says this specific setting also needs the Initialize button
  pressed once to take effect in the running session. Confirmed live:
  Tune keyed the radio into a dummy load.

## Lessons

- **A radio's CI-V echo-back setting can silently break any tool that
  only reads up to the first frame terminator.** Real production CAT
  software has to handle an echoing bus; this project's tools didn't,
  and it looked like intermittent hardware flakiness until traced with a
  byte-level capture.
- **"It shows as transmitting" isn't proof the radio is keyed.** Two
  independent things can each look fine on their own (CAT control, and
  the app's own TX state) while a third, separate setting (PTT wiring)
  is the actual gap - check the dummy load/TX light, not just the app.
- **A stale, already-running process won't pick up a code fix.** One
  false alarm mid-session was just Channel Picker still running the
  pre-fix code in memory; closing and relaunching it resolved it
  immediately.
